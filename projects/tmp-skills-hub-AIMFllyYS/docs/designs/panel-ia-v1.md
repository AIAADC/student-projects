## 1. 为什么要重构,而不是继续加按钮

面板现在的形状是:157 个独立手风琴,每个里面 23 个独立开关。它暴露了 3611 个一次性单点写操作,
却没有任何「成套地想这件事」的入口。加 6 个按钮不会改变这一点。

从第一性原理看,这个产品的中心对象**不是 skill,是链接集合**。

「统一管理」的实质是回答一个问题:*哪些技能对哪些 Agent 可见。* 查看、编辑、翻译、分析、
统计全都是为这个决定服务的辅助信息。领域里只有四个实体和**一个关系**:

| 实体 | 规模(当前) | 说明 |
| --- | --- | --- |
| Skill | 157(目标 1000+) | 内容 + 哈希 + meta + origins + 生命周期(活跃/归档) |
| Client | 23 | 一个 Agent 读取技能的目录 |
| Group | 内置 + 用户定义 | 技能的命名子集 |
| Usage | 每 skill 计数 | 调用事实数据 |
| **Link(关系)** | **157 × 23 = 3611** | skill × client 的二元关系,**产品的真正主体** |

界面的形状必须和数据的形状同构。现在不同构,所以怎么加按钮都像壳。

## 2. 三栏骨架:作用域 → 集合 → 检查器

采用 list-detail 三列(Apple `NavigationSplitView` 的经典形态:**前列的选择驱动后列的内容**)。

    ┌──────────────┬───────────────────────────────┬──────────────────────┐
    │ 作用域 Scope  │ 集合 Collection                │ 检查器 Inspector      │
    │  14rem 固定   │  1fr                          │  28rem 固定           │
    ├──────────────┼───────────────────────────────┼──────────────────────┤
    │ 全部技能 157  │ [搜索…]            [排序 ▾]    │ lark-base            │
    │              │ ☐ 全选 · 已选 0                │ hash · origins · 次数 │
    │ 分组          │ ──────────────────────────    │ ┌─内容─┬─客户端─┬─分析┐│
    │  开发 42      │ ☐ lark-base       12/23 ●     │ │文件树 │ 23 行  │相近 ││
    │  设计 18      │ ☐ lark-doc         0/23       │ │正文   │ 行级   │冲突 ││
    │  ＋新建分组    │ ☐ agent_mgmt       3/23 ●     │ │编辑/译│ 开关   │     ││
    │              │ …(虚拟滚动)                    │ └──────┴───────┴────┘│
    │ 客户端        │                               │ 归档此技能(可撤销)    │
    │  claude 87    │                               │                      │
    │  cursor 12    │                               │                      │
    │ 来源          │                               │                      │
    │ 归档区 3      │                               │                      │
    │ 报告 · 一键恢复│                               │                      │
    └──────────────┴───────────────────────────────┴──────────────────────┘
     选中 > 0 时从底部浮出常驻条:
     [ 已选 12 项 ] [启用到…▾] [挂到分组…▾] [停用] [⋯ 归档] ————————— [清除]

**D1. 三栏取代内联手风琴。**
实测手风琴全展开 16032 个 DOM 节点,而内容区被压在 `max-h-96` 里读长文档。改成单一检查器后
DOM 恒定、查看器拿到全高、不再存在「同时展开 20 个」这种无意义状态。

**D2. 窄屏退化。** < 1024px 时收掉作用域列,检查器改为覆盖层;不做移动端专门设计(内部工具)。

## 3. 核心决策:关系按「行」暴露,不按「格」暴露

3611 个交叉点是典型的权限矩阵问题。业界对此的一致结论是:**不要渲染完整的 N×M 网格**,
改用「选择器 + 详情」两栏、行级开关、稀疏存储、过滤与渐进式披露收窄范围。
(反例是 UX StackExchange 上那个 418×153 = 6.4 万个开关的页面,公认不可用。)

落法:

| 位置 | 显示什么 | 不显示什么 |
| --- | --- | --- |
| 集合列的行 | **聚合**:`12/23` + 一个状态点 | 23 个开关 |
| 检查器「客户端」页 | 当前这**一个** skill 的 23 行,每行一个开关 | 其他 skill |
| 作用域列选中某客户端后 | 集合列切到「该客户端视角」,行上的开关就是这一个客户端的 | 其他客户端 |

**D3. 双向视角是同一份数据的两种切片**,不是两个功能:以 skill 为主体看「它去了哪些客户端」,
以 client 为主体看「它装了哪些 skill」。第二种视角才是「给 claude 配一套」这类真实任务的入口。

**D4. 状态一律文字优先。** `12/23` 是文字;状态点只是辅助,不独立承载信息。与 ui-design-v1 §2
「颜色只表达语义」一致,也满足可访问性(不靠颜色/图标单独表达状态)。

**D5. 每个链接状态要能说清来源。** 权限矩阵的通用要求是「一个勾不够,必须说清这个状态从哪来」。
本项目对应的三种来源:**受管链接**(台账里有)、**用户自己的目录占名**(`unregistered-conflict`,
绝不覆盖)、**悬空链接**。检查器的客户端行必须区分这三种,不能都画成「关」。

## 4. 批量:一次原子提交,不是 N 次请求

这是本项目比通用建议更强的一条约束,来自内核既有能力。

`core` 的 `applyLinkSet(storeRoot, { targetDir, entries })` **本来就接受整个条目集合**,
内部 journal 先行 + 逐条切换 + 失败按 journal 回滚(见 [core-patterns.md](../conventions/core-patterns.md) §2)。
面板的正确用法因此是:

    累积 pending 变更 → 一次 POST /api/links/apply → core 一次原子切换 → 一次响应回写

**D6. 禁止把批量实现成循环调用单条端点。** 现在每格一个 POST、每次成功后整表重拉 129 KB;
按这个做法批量启用一个分组(42 个 skill)= 42 次请求 + 42 次全量重拉。而 `applyLinkSet` 一次就能做完,
且比 42 次单独调用**更安全**(要么全成、要么回滚到变更前)。

**D7. 三态 + 批量保存。** 每个待变更条目有 current / pending / displayed 三态:改动先进 pending
(视觉上标记未保存),点「应用」一次提交,响应回来逐条落成 saved 或 error。这既是权限矩阵的通用
做法,也正好对上 `applyLinkSet` 的返回结构(`created[]` / `removed[]` / 结构化失败 + `at`)。

**D8. 破坏性动作靠 dry-run 预览,不靠文案吓人。** CLI 已有 `--dry-run`,提成端点即可:
批量条的破坏性动作先给 diff——「将新增 N 条 / 摘除 M 条 / **冲突 K 条**」,确认后才执行。
落点被用户自己的文件夹占住这种情况,必须在**预览阶段**就显形,不能等执行时才报错。

## 5. 选择模型的硬规则

批量操作的通用规范照抄成验收标准,逐条可测:

1. 表头 master checkbox 三态:全选 / 未选 / **部分选(indeterminate)**
2. 浮动条在选中数 0→1 时出现,回到 0 时消失;**常驻显示选中计数与「清除」**
3. 最多 3 个内联动作,第 4 个起进 overflow 菜单
4. 动作用**动词**命名(「归档」「启用到…」),不用「应用」「确定」这类空词
5. 动作按安全→危险排序,破坏性动作放最后并视觉分隔
6. **过滤、排序、搜索变化不得静默清空选择**
7. 「全选」只作用于**当前可见集**;要跨过滤集必须是独立的、显式的一步,且把最终计数显示在动作按钮旁
8. 破坏性批量必须二次确认;单条破坏性动作用「toast + 撤销」代替确认弹窗

**D9. 软删除用可撤销,不用确认弹窗。** `archive` 本来可逆(zip 躺在归档区),所以归档后给
toast + 「撤销」。**真删除永不提供**,只显示归档路径由用户自己动手(架构规范 §4 铁律)。

浮动条的视觉表达受 ui-design-v1 禁用清单约束:**不能用阴影或毛玻璃**做层级。用 `bg-white`
实体条 + 1px 上边框 + 与页面同宽,靠位置和实体感区分层级。

## 6. 动作面必须先可编程,UI 按钮只是它的一个视图

**D10. 所有管理动作先注册成「可编程动作」,再挂 UI。** 每个动作有稳定的 id、参数、
预览能力和执行入口;按钮、菜单项、命令面板项都只是同一个注册表的不同渲染。

理由有两个,都不是审美问题:
- 面板要成为主操作台,而这批用户的肌肉记忆是打字。⌘K 命令面板把 CLI 动词原样搬进面板,
  一个入口穷尽所有动作,不用记按钮在哪一栏。
- 智能层要写成 Skill 而不是代码(AGENTS.md 铁律)。Agent 通过 CLI 操作面板背后的同一套动作,
  前提就是动作有稳定的可编程形态。

命令面板本身排在最后做,但**动作注册表要在批 9 第一个 issue 就立起来**,否则后面每个按钮都会
各写一套私有逻辑,再想统一就晚了。

## 7. 端点缺口(http-api v1 增量)

| 端点 | 用途 | 对应 CLI |
| --- | --- | --- |
| `POST /api/adopt` | 收录:本地路径 / GitHub / skills.sh 链接 | `adopt` |
| `POST /api/links/preview` | 批量变更的 dry-run diff(含冲突) | `enable/disable --dry-run` |
| `POST /api/links/apply` | 批量原子切换(一次 `applyLinkSet`) | `enable/disable` |
| `POST /api/skills/:hash/restore` | 从归档区恢复 | (需新增 CLI 动词) |
| `POST /api/groups` `PATCH /api/groups/:id` `DELETE /api/groups/:id` | 分组增删改 | `group add/rm/edit` |
| `POST /api/analyze` | 相近/冲突分析(模型只出建议) | `analyze` |
| `GET /api/verify` `GET /api/doctor` | 四检报告 | `verify` / `doctor` |
| `GET /api/backups` | 列备份快照 | `backup list` |
| `POST /api/backups/preview` | 一键 reset 的 dry-run 预览(D8) | `backup restore --dry-run` / `reset --dry-run` |
| `POST /api/reset` | 确认后在当前 ui 进程跑完 `reset`（还原 + 旁路 + 再收录） | `reset` |

规则不变:信封与错误 code 复用 [json-contract-v0.md](../specs/json-contract-v0.md);
写端点复用 CLI 同一份实现(行为不漂移);服务只绑 `127.0.0.1`。
「恢复到初始化前」动作 id 为 `reset`(`destructive` + `supportsPreview`),放在作用域「报告」,不放浮动批量条;**不得**复用归档恢复的动作 id `restore`。二次确认 = 预览 + 输入短语 `reset`(D8),不是空吓文案。

## 8. 性能口径(带阈值,可测)

审计已确认当前没有死循环,以下是**重构后不许退化**的红线:

| 指标 | 阈值 | 测法 |
| --- | --- | --- |
| 点击一个 skill 后 4 s 内 fetch 数 | ≤ 2 | CDP 探针 |
| 操作后静置 10 s 的 CPU 增量 | ≤ 0.1 s | CDP 探针 |
| 单个长任务 | ≤ 200 ms | PerformanceObserver longtask |
| 1000 个 skill 时的列表 DOM 节点 | ≤ 3000(虚拟滚动) | CDP `Performance.getMetrics` |
| 批量启用 42 个 skill 的请求数 | **1** | 网络面板 |

**D11. 不新增运行时依赖。** 虚拟滚动自己写(固定行高 + 容器 `overflow` + 切片渲染,约 60 行),
状态继续用 `useState`/`useReducer`。理由是 AGENTS.md「尽量不引入」,且这两处自研成本低于依赖成本。
突破口径:若施工中证明自研做不到(例如可访问性无法自证),在 PR 里说明理由后允许引入。
