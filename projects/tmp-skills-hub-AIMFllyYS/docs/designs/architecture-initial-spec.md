## 0. 本文管什么、不管什么

**管**：分析方法、系统分块、资产模型、六个操作的架构语义、接口抽象点、依赖 DAG、架构层面的不做清单。

**不管**：具体实现细节（哈希算法选型、Windows symlink 权限、目录命名、UI 布局）。这些在后续 specs 里定，定的时候引用本文对应条目。

一句话背景：**用户是社团自己，要管的资产是 Skill，第一件可交付的事是「统一看」。** 本文把这句话展开成可以开工的架构。

## 1. 架构决策方法论（最高优先级，先于一切具体结论）

会议的最大产出不是某个结论，而是一套分析顺序。**以后任何新模块、新需求进入架构讨论，必须按这个顺序走**：

### 1.1 三问开场

任何功能立项前先回答，答不出就不开工：

1. **服务谁？** 人（社团成员）还是长时间运行的自动化 Agent？——本项目：**人**。
2. **管什么资产？** ——本项目：**Skill**（本质是一个文件夹）。
3. **CRUD 在哪？** 没有 CRUD 就没有业务。对该资产的存 / 用 / 改 / 删 / 范围 / 创建分别落在系统哪一块？

### 1.2 决策甬道

- 从**用户的第一决策**出发（"我看到一个好 skill，想存下来"），自上而下推。
- 每一步只回答当前这一步的问题；**走到可以停的地方就停，把接口先抽象出来**，不实现后面的步。
- 后面的步（如「有用」的判定、AI 推荐）想到了就**登记进 issue / backlog**，不当场展开，更不提前实现。

### 1.3 决策纪律

- **固定需求不辩论**：做「统一查看」必然联想到搜索框、来源分类、tag。这类需求可以决定做或不做，但不花会议时间讨论定义。
- **不把后面的步提前争**：一个词（如「有用」）在不同场景意思不同，还没轮到的步不拿出来让全场停下对齐用词。
- **提需求的前提是你在用**：不用 skill 的人先不提 skill 需求。
- **提最高杠杆的需求**：不是随口一句，而是问"从 1 做到 5 之后，下一步杠杆最高的是什么"。
- **能绕过的 block 先绕过**：例如账号系统 block 社区玩法 → 用授信仓库绕过，同时承认"不做账号，社区玩法永远玩不出来"，把它留在图上。
- **复用被做过一万遍的标准做法**：项目级/全局隔离、符号链接语义等，各 Agent 已实现的机制直接用，不重新发明。
- **整理成 DAG 再开工**：线性鱼骨 → 工程 DAG，识别核心块，把依赖画出来，issue 写对了才允许并行。

## 2. 系统分块与依赖 DAG

从决策甬道收出来的核心块有四个，依赖方向如下：

```text
[A 库存与镜像层]  ← 一切的地基
      │
      ├──→ [B App 壳（统一查看）]        ← 第一件可交付
      │           │
      ├──→ [C 分享层（授信仓库）]         ← 可与 B 并行，B 依赖 A 即可
      │           │
      └──────────┴──→ [D 社区与统计层]   ← 被账号 + 使用数据双重 block，后置
```

| 块 | 职责 | 状态 |
|---|---|---|
| **A 库存与镜像层** | 统一目录、内容哈希去重、符号链接回各 Agent、收录入口（本地扫描 / GitHub 链接） | 第一批 |
| **B App 壳** | Web 应用：列表、搜索、来源分类、tag。只读 A 的产出 | 第一批（第一件可交付） |
| **C 分享层** | 授信成员写统一 Git 仓库，链接分发；绕过账号 | 第一批可开（薄版） |
| **D 社区与统计层** | 使用量统计 → 个人主页 → 精选/排行；依赖账号（或幂等登录接入）与使用数据 | 后置，画在图上 |

**Block 规则（写 issue 时强制引用）**：

- 后端没有使用统计，前端**交付不了**主页/排行 → D 内部先后端后前端。
- 没有账号（或授信名单），D 整块不开工；C 不受此 block。
- B 只依赖 A 的数据产出，**不依赖** C、D——壳子第一天就能立。
- A 不依赖任何块，最先做。

## 3. 资产模型规范

### 3.1 Skill 的定义

- 一个 Skill = **一个文件夹**，不是单文件。入口是 `SKILL.md`。
- **通用层**：`name` + `description`。所有客户端都能读，这两个字段是收录的最低要求。
- **适配层**：各家 YAML 扩展（如 OpenAI 侧的 display name）。缺失不影响可用性；精致适配 = 读各家维护了什么再补，**不是收录门槛**。

### 3.2 身份与去重

- 一个 Skill 的唯一标识 = **整个文件夹内容的哈希**，不是文件名，不是路径。
- 内容变 → 哈希变 → 视为新版本。系统需要维护「哈希 ↔ skill」的对照。
- 目标性质：**不漂移**——在 Claude 里改和在 Codex 里改，落到的是同一份原件。

### 3.3 命名

- `name`、路径、目录一律**英文**（Agent 读取与路径稳定性优先）。
- 中文展示走 display name 一类**展示层字段**，渲染时才用，检索与召回仍按 `name`。

### 3.4 存储介质

- 现阶段：**文件系统目录**。
- 接口先抽象（见第 5 章），技能量到 1000+ 再评估换介质。**不提前做数据库**。

## 4. 六个操作的架构语义

这是整个架构最核心的一条：**库存归我们，语义归符号链接，隔离归各 Agent 已有机制**。

| 操作 | 架构语义 | 我们要做的 | 我们不做的 |
|---|---|---|---|
| **存** | 镜像进统一目录，算哈希去重，在各 Agent 目录放符号链接 | 目录约定、哈希、链接；**收录前明确告知并获得授权**，绝不静默搬走用户已有技能 | 不做「先定义什么算有用」 |
| **创建** | 在库存内分配目录 → 内容写入 → 定稿入正式清单。**与「存」是反向数据流**：存是 content-first（内容先存在再入库），创建是 location-first（先占位再写内容） | `new` 命令占名写模板、`new commit` 定稿入清单、`new discard` 移入归档区。创建不复用 `adoptSkillFolder`（内容哈希去重在创建期不成立——两个同模板空 skill 内容相同但不是同一个 skill） | 不做内容质量判断——AI 写得好不好交给 Skill 层与 `analyze` |
| **用** | Agent 从自己目录发现链接即能用 | 保证链接有效；**通过链接集合控制哪些 skill 对 Agent 可见**（渐进式披露，见 [cli-commands-v0.md](../specs/cli-commands-v0.md) §4） | 不重写各 Agent 内部的加载算法与相关性检索；不做「更牛的检索」 |
| **改** | 改链接 = 改原件 = **全局改**，天然不漂移 | 无需新做 | 不做多副本同步 |
| **删** | 删链接 ≠ 删原件；Agent 读不到即等于卸下 | 提供摘链接的入口（`disable`）；另提供软删除（`archive`，移出活跃区并归档为 zip） | **不提供真删除**——彻底删除只向用户显示归档路径，由用户自己动手 |
| **范围** | 项目级/全局 = 链接挂在项目目录还是用户目录，复用各 Agent 已有隔离 | 只决定链接放哪一侧 | 不自建隔离机制 |

> **§4 修订记录（2026-08-19，#169）**：补第六行「创建」。根因：决策甬道 §1.2 的起点是「我看到一个好 skill，想存下来」，全程从既有 skill 出发；「我要做一个新 skill」是另一条起点不同的甬道，此前未走过，导致创建在客户端 skills 目录里产生的真目录逃逸出链接语义。详见 [creation-path-analysis.md](../issues/skill-creation-path/creation-path-analysis.md)。

## 5. 接口抽象点（走到这里停下，把接口抽出来）

会上的原则：可能会走到某一步，所以**先把接口抽象了**，但不实现。这些是**换介质 / 换来源时才落地的登记**，不是当前运行时合同。

**当前第一版是函数内核**，不要按 `implements StorageProvider` 一类对象模型写新代码：

| 能力 | 当前运行时缝（以此为准） | `interfaces.ts` 类型 | 已预见的未来（只登记，不做） |
|---|---|---|---|
| **存储** | `adoptSkillFolder` / `readStoreIndex` / `archiveSkill` / `allocateDraft` / `commitDraft` / `discardDraft`（文件系统目录） | `StorageProvider`：**无实现**。其 `add`/`archive` 签名已与函数内核不一致，不得当施工合同 | 1000+ 时换数据库或其他介质 |
| **收录来源** | 本地扫描 = `scan` + `adopt`；GitHub / skills.sh = CLI 上鸭子类型的 `canHandle`/`fetch`（网络留在 cli） | `SourceProvider`：仅 GitHub 收录类形状相近，**没有 `implements`** | 浏览器插件、Agent 对话代存、市场页面 |
| **客户端** | 按目录形状发现 `discoverClientRoots` + 集合切换 `applyLinkSet`（不维护品牌名单，不按单条 `link/unlink`） | `ClientAdapter`：**无实现**，且是 #21 之前的单条挂链模型，与现行原子集合切换冲突。禁止按它写新代码 | 各家 YAML 精致适配 |
| **身份** | 分享推送读 `GITHUB_TOKEN`；无授信对象、无 `canWrite()` | `IdentityProvider`：**无实现**。D 块账号系统到来之前不要补一层恒真包装 | 账号 / 统一登录；接入必须**幂等** |

兼容性要求：在我们提供收录入口之前，用户已经在用「对 Agent 说」和「手动 clone」。新入口**兼容**这些路径，不拦截、不接管。

> **§5 修订记录（2026-08-19，#169）**：创建操作不引入第五个接口。`allocate`（占位）和 `commit`（定稿）落在存储函数上——创建的产出仍是库存中的一条记录，形态相同、介质相同。新开第五个接口会让「收录来源」与「创建来源」长期打架。创建不走来源 `fetch` 是因为它没有 input 可以拉取。
>
> **§5 修订记录（2026-08-22，#192）**：第一版并未按四个接口对象落地。真实缝是上表「当前运行时缝」。类型文件保留作未来换实现时的登记，施工以函数内核为准。状态由 `review` 转为 `accepted`。

## 6. 架构层面的不做清单

| 不做 | 理由（来自会议） |
|---|---|
| 公开技能市场 / 所有人都要装的包管理器 | 用户不是全网用户；做不过 skills.sh 等成熟产品，"真不了的时候回归本质" |
| 未经告知搬走用户本地技能 | 产品没有宣称代管就动手，是授权问题，不是技术问题 |
| 替各 Agent 重写内部的加载算法与相关性检索 | 各家已有方案；那是自己的另一个 focus，不是本项目第一天的事。**注意**：用链接集合控制 skill 可见性（渐进式披露）不在此列——那是 §4「范围」原有语义的延伸，不碰各家内部逻辑 |
| 局域网分享 | 成员不全在局网，直接上云 / Git 托管 |
| 第一天做账号系统 | 授信仓库可绕过；但登记：不做账号，社区玩法出不来 |
| 第一天做「有用」判定 / 评测 / AI 推荐 | 是后面的步；想到即登记，不提前争 |

完整后置清单（含浏览器插件、使用统计、主页、排行等）见 [backlog-from-first-sync.md](../issues/backlog-from-first-sync.md)。

## 7. 工程执行规范

1. **先 DAG 后 issue，先 issue 后代码**。每个 issue 必须写清：属于哪个块（A/B/C/D）、依赖哪些 issue、被谁 block。
2. **能并行的并行**：A 里的哈希去重与 B 的壳子骨架可并行；前提是 issue 里的依赖写对。
3. **和 AI 协作同样走这套甬道**：把上下文给足，让 AI 按 DAG 推进；人协作的价值在真正产出的部分与获得这种拆法本身。
4. **每次架构讨论产出落文档**：决策进本文或 designs/，后置进 issues/，纪要进 updates/。想到了但不做的事，**第一天就躺在列表里**。
5. 分支、commit、PR 规范沿用 [AGENTS.md](../../AGENTS.md) Git Workflow 一节。
