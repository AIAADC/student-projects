# 确定性内核关键模式

> 本文档是 `AGENTS.md` 中「确定性内核铁律」的完整版。
> 这些不是风格偏好,是数据一致性约束——违反任意一条,「同一 skill 跨机器同哈希、跨 Agent 不漂移」就破功。
> 语义来源:架构初始规范 §3(资产模型)、§4(五个操作)。

## 一、store 可写，哈希是快照

> 本节在 2026-08-16 被修订。原文写的是「store 不可变、更新产生新哈希的新版本」，与架构规范 §4「改链接 = 改原件 = 全局改」以及面板要求的「可编辑写回」直接冲突：若链接指向 store 原件，Agent 一改，`store` 里的内容就和记录的哈希不符，「哈希唯一标识 skill」当场破功。按「遇到架构矛盾先修文档」的原则改为下述口径。

- `skills/<name>/` 是**可写的活跃副本**，符号链接直接指向它。用户在任何 Agent 里改、或在面板里编辑，改到的都是这一份——这正是「全局改、不漂移」的实现方式。
- `index.json` 里的哈希是「**入库或上次 `verify` 那一刻的内容指纹**」，不是随时可信的身份。
- 一致性靠 `verify` 维持:重算哈希 → 报告漂移 → 用户确认后把旧内容归档成 zip 并更新记录。**归档区天然构成版本历史**，回滚 = 从归档取回。
- 去重仍然按内容哈希做(录音稿要求),但那是**入库判定**逻辑,不是目录命名逻辑。布局细节见 [store-and-paths-v0.md](../specs/store-and-paths-v0.md)。

## 二、受管条目集合的原子切换

> 本节在 2026-08-16 被修订。原文要求整目录重命名替换(`active` → `active.old`)。但链接落点是 `~/.claude/skills/` 这类目录,**它同时装着用户自己的真实技能文件夹**——本机实测 26 个这样的 root、579 份 skill。整目录 rename 会连带换掉用户非受管的技能,直接命中「未告知就移动用户本地 skill 目录」这条 Never。

变更某个客户端目录下的链接集合时:

1. **只碰 `links.json` 台账里登记过的条目。** 遇到未登记的同名条目 → 报错中止,绝不覆盖;要删除的条目磁盘上不是链接(被用户替换)→ 同样报错中止。
2. **journal 先行(预写日志,落在 `<storeRoot>/tmp/`)**:把本次将新建/摘除的全部条目写进 journal 再动手。
3. 逐条执行:摘除 = `unlink`(只删链接不跟随);建立 = `symlink`(junction/symlink)或复制(`copy` 降级);单条操作本身原子。
4. 任一步失败 → 按 journal 逆序回滚(摘掉已建、按旧条目重建已删),不落半成品;成功与失败两条路径都清理 journal 与 tmp 残留。
5. 成功后更新台账并清理 tmp。

> **2026-08-16 修订理由(与 #21 同步)**:原口径为「在 `<storeRoot>/tmp/` 构建完整新集合,再逐条 rename 进目标」。但库存与客户端 home 可能**跨卷**(如库存 D:、home C:),跨卷目录 rename 必然失败(EXDEV),tmp 构建方案不可行;链接创建本身逐条原子,集合级原子性改由 journal 回滚保证。rename 顺序约束仍有效:先 unlink 旧链接(不跟随),再建新链接——rename 不允许目录覆盖非空目录。

**禁止**对客户端的 skills 目录做整目录重命名或整目录删除,无例外。

## 三、哈希确定性

`hashSkillFolder`(packages/core/src/hash.ts)的三条不变量:

1. **顺序无关**:文件按 POSIX 风格相对路径字典序排序后哈希,与目录遍历顺序、操作系统路径分隔符无关;
2. **路径参与哈希**:每个文件哈希 `相对路径 + "\0" + 内容`,区分「同内容不同文件名」;
3. **哈希原始字节,不做换行归一化**:跨机器换行一致由仓库层保证(`.gitattributes` 统一 LF),不在哈希层做变换——哈希层的变换会让"磁盘上的内容"和"身份"脱钩,排查问题时无法对账。

忽略项(`.git`、`node_modules` 等)的清单变更等于**全库哈希迁移**,必须走 issue 评审。

## 四、链接语义与权限(2026-08-16 修订)

> 本节依据 链接语义调研(docs/audits/link-semantics-research-2026-08-16.md)修订(联网查证,每条结论附来源)。原「各 Agent 读目录内容的行为一致」表述不准确,按查证结果细化。

- 本地开发环境是 Windows:普通用户创建 symlink 需要开发者模式或管理员权限;junction 与 hardlink 无需提权(hardlink 仅文件,本项目不用作目录挂载)。
- **目录链接优先用 junction**(fs.symlink(target, path, "junction")),目标必须是**绝对路径、同 NTFS 卷**;非 Windows 平台用目录 symlink(无特权,可用相对目标)。
- **条目级链接(链接放在真实存在的客户端 skills 目录内)对 agent 加载器读取一致;但目录整体是链接、UI 菜单可见性、客户端自动更新三类场景不可靠**(Claude Code #38051/#68318/#50052),对应客户端需降级为复制——落地前 spike 需实测其余客户端的加载与 UI 显示。
- **删除链接必须先 lstat 判型再 unlink,绝不用 Remove-Item -Recurse -Force / del /s /q 删除含链接的树**(会跟随 junction 删到链接目标,PowerShell #26913 灾难性数据丢失)。
- **原子切换的 rename 顺序:先 unlink 旧链接(不跟随),再 rename 新链接**;rename 不允许目录覆盖非空目录,不能整目录覆盖。
- store 内部不允许出现链接;扫描时遇到链接不展开,交给上层校验报错。

## 五、智能层写成 Skill,不写成代码

来自 SPM 设计的核心主张,skill-hub 沿用:**只有 Agent 做不了的事才写成代码**。

| 写成代码(core/cli) | 写成 Skill(交给 Agent) |
|---|---|
| store 增删、哈希、lockfile —— 需要原子性与精确性,不能有幻觉 | 健康检查、安全审查 —— 读文本做判断 |
| symlink 增删 —— 必须快速、原子、确定 | 分类/tag 建议、"有用"判定 —— 语义理解 |
| 本地数据服务 —— 会话之外运行 | 收录时的对话式引导 —— 天然对话能力 |

判断口径:**错了会破坏数据一致性的,进 core;错了只是建议不好的,写 Skill。**

## 六、已验证的平台事实（引用时不必重新验证）

- Claude Code 只有 `--add-dir` 指定的目录支持 skill **热加载**;默认 `.claude/skills/` 只在启动时读取。链接挂载位置的设计要考虑这一点。
- `SKILL.md` 的 `name` + `description` 是所有客户端都能读的通用层;各家 YAML 扩展(display name 等)是适配层,缺失不影响可用性,**不是收录门槛**。
