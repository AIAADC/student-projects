# 版本号规则（VERSIONING）

本文件是 PocketWebShell 版本号的**唯一权威规范**，`AGENTS.md` 引用本文件。
条款中的 **必须 / 禁止 / 应当** 按 RFC 2119 语义解读。

## 1. 术语与格式

| 位置 | 官方术语 | 中文 | 示例（0.1.1001） |
|---|---|---|---|
| 第一位 | major version | 主版本号 | `0` |
| 第二位 | minor version | 次版本号 | `1` |
| 第三位 | patch / micro | 修订号 | `1001` |

- `versionName` **必须**为 `MAJOR.MINOR.MICRO` 三段十进制非负整数；**禁止**前导零；**禁止**附加先行版（`-rc.1`）或构建元数据（`+date`）后缀。
- `versionCode` 是面向 Android 包管理器的单调递增整数，与 `versionName` 位数规则相互独立。
- 二者均定义于 `app/build.gradle.kts`；Git 标签格式为 `v<versionName>`。

## 2. 规范性规则

- **R1（默认递增）**：每次发布**必须**且仅**必须**将第三位 +1。更新规模大小不影响本规则——成体系的大更新也只动第三位。
- **R2（禁止进位）**：第三位**永不**向第二位进位：`0.1.9 → 0.1.10`、`0.1.1000 → 0.1.1001`，位数无限增长亦然。
- **R3（高位冻结）**：第一、二位**仅当用户明确指示时**才可变动；任何自动流程**禁止**提升高位。高位 +1 时其右侧所有位归零（如用户指示升第二位：`0.1.1001 → 0.2.0`；指示升第一位：`0.5.12 → 1.0.0`）。
- **R4（versionCode）**：每次发布 `versionCode` **必须**严格 +1，**禁止**复用、回退或跳号，与 `versionName` 位数变化无关。
- **R5（不可变发布）**：同一 `versionCode` / `versionName` **禁止**对应两个不同产物；任何修改**必须**以新版本号发布。
- **R6（发布的定义）**：「一次发布」= 一次交付给用户的打包构建（debug 交付或正式 Release）。代码提交、分支合并不构成发布。

## 3. 操作示例

| 场景 | 操作 | 结果 |
|---|---|---|
| 日常发布 | 第三位 +1 | `0.1.1 → 0.1.2` |
| 第三位到达 9 / 99 / 999 … | 继续 +1，不进位 | `0.1.9 → 0.1.10` |
| 用户明确指示「升第二位」 | 第二位 +1，第三位归零 | `0.1.1001 → 0.2.0` |
| 用户明确指示「升第一位 / 发 1.0」 | 第一位 +1，后两位归零 | `0.5.12 → 1.0.0` |
| 任意一次发布 | `versionCode` +1 | `2 → 3` |

## 4. 发布同步清单

每次版本号变化**必须**在同一提交内同步以下三处，缺一视为发布未完成：

1. `app/build.gradle.kts`：`versionCode`（+1）与 `versionName`；
2. `CHANGELOG.md`：按 Keep a Changelog 格式新增 `## [versionName] - YYYY-MM-DD` 条目；
3. 应用内「我的 → 项目更新日志」页内容。

## 5. 发布工作流（debug 先行）

本节定义从代码修改到正式 Release 的完整流转。核心原则：**release 是 debug 的确认形态，二者同号；用户的明确确认是唯一的发布闸门。**

- **W1（debug 先行）**：任何版本在发布 release 之前，**必须**先以相同版本号的 debug 构建交付用户测试。在用户明确确认测试通过之前，**禁止**执行任何发布动作——包括构建 release 包、合并到 `main`、打 tag、创建 GitHub Release。
- **W2（同号发布）**：release 构建的 `versionCode` / `versionName` **必须**等于用户确认通过的那个 debug 构建。二者是同一版本的两种构建形态，不是两个版本。
- **W3（返工消耗号码）**：debug 测试未通过时，修复后**必须**按 R1/R4 递增版本号并同步 §4 全部三处，再交付新的 debug 构建。被否决的号码**禁止**复用（R5 的直接推论）；即使该版本从未存在过 release 形态，也**必须**保留在 `CHANGELOG.md` 和应用内更新日志中。
- **W4（无变化不递增）**：代码与资源零变化的纯重打包不构成新发布（R6），**禁止**消耗新版本号。
- **W5（Release 说明汇总）**：GitHub Release 的说明**必须**覆盖自上一个已发布 release 至本次发布之间的所有版本（含仅有 debug 形态的版本），因为中间版本在 Release 页面上没有独立条目。表述方式按内容性质选择：连续版本修复同一问题的，合并为一条说明；涉及多个不同问题的，并列分条；也可采用「X 至 Y 更新了什么」的区间式表述。
- **W6（发布四步）**：用户明确指示发布后，**必须**按序执行：
  1. **合并**：若当前不在 `main`，按 Git 工作流将代码合并到 `dev`，再经 PR 合入 `main`；
  2. **发布**：以用户确认的版本号构建 release 包、打 tag、创建 GitHub Release（说明按 W5 汇总）；
  3. **同步**：将本地与远端的所有分支和 tag 同步至最新；
  4. **归位**：切回 `dev` 分支，继续开发。

### 5.1 场景推演

设上一个已发布的 release 为 `0.1.(N-1)`，本轮开发从 `0.1.N` 开始：

1. 交付 `0.1.N` 的 debug 构建 → 用户测试发现问题；
2. 修复 → 递增为 `0.1.(N+1)`，同步 §4 三处 → 交付新 debug → 仍有问题；
3. 再修复 → 递增为 `0.1.(N+2)`，同步 §4 三处 → 交付新 debug → 用户确认通过；
4. 用户指示发布 → release 版本号为 `0.1.(N+2)`（**不是** `0.1.N`）→ 按 W6 四步执行；
5. GitHub Release `0.1.(N+2)` 的说明按 W5 汇总 `0.1.N` ~ `0.1.(N+2)` 三个版本的全部更新；`0.1.N` 与 `0.1.(N+1)` 仅有 debug 形态，号码已被消耗，永不复用。

## 6. 与 SemVer 的关系

- **借用术语**：major / minor / patch 命名来自 Semantic Versioning 2.0.0（semver.org）。
- **刻意偏离**：本规则冻结高位、第三位不进位，不符合 SemVer 第 6/7/8 条的进位要求——这是有意为之的产品姿态。业界先例充分：TeX 版本号渐近 π（小数位无限延伸）、Linux 2.6.x 八年数字管理、微信 8.0.x 五年、Office 16.0 十一年、ZeroVer 运动。
- **适用前提**：本项目是独立应用而非被依赖的库，没有公共 API 消费者，SemVer 的兼容性承诺前提不成立。若未来对外发布 SDK / API，**必须**重审本规则。

## 7. 历史记录与已知风险

- **计数重置（2026-08-30）**：版本计数从旧线（止于 `0.2.0` / `versionCode=2`）重置，新线自 `0.1.0` / `versionCode=1` 起，`CHANGELOG.md` 有明确记录。
- **覆盖安装风险**：新线 `versionCode` 低于旧线，已安装旧版 `0.2.0` 的设备**无法覆盖安装**，必须先卸载再安装。
- **规则误用记录（2026-08-30）**：曾将第二位误升至 `0.2.0`（新线），已回退为 `0.1.1` 并同步修订本文档与 `AGENTS.md` 的规则表述。教训：除用户点名外，任何情况下不得触碰第一、二位。
