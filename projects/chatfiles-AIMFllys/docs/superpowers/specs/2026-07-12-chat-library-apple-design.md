# ChatFiles 聊天素材库与 Apple Design 设计规格

## 目标

在不改变“纯本地、原始数据只读、私密数据不入 Git”的前提下，把聊天页升级为一座可检索的会话素材库：保留现有全局左轨，在聊天页增加二级大导航；选中会话后，右侧按作品、文档、Skills 工具、链接、聊天文字展示统计、检索结果和缩略图，并支持浏览器内本地预览。全局视觉遵循已安装的 `apple-design` skill，完整支持浅色、深色与系统主题。

## 设计依据

- `docs/refer.png` 只提供信息架构：窄全局轨道、宽二级列表、右侧标题/统计/Tab/网格。
- `apple-design` 提供交互与视觉原则：即时反馈、空间路径一致、克制材质、系统字体、语义颜色、可中断状态变化、减少动态/透明度/高对比度降级。
- 当前项目继续使用 React 19、TypeScript、Express、SQLite、Lucide 与现有文件预览器，不引入新的 UI 框架。
- 中文文件、文案和数据始终按 UTF-8 读取和写入；测试增加乱码与身份一致性检查。

## 方案比较

### 方案 A：前端从全部消息即时推断

实现快，但大群会一次加载数万条消息；文件与消息没有稳定关联，按标题猜测会产生错误归属。否决。

### 方案 B：独立资产索引与证据键（采用）

解析阶段保留 `message_uid`、`local_id`、`sort_seq`、基础/原始类型；资产导出阶段先用完整消息定位字段对齐 `MessageResourceInfo`，再要求同一会话范围与资源 hash 或应用消息 XML 标识精确一致。API 只读取索引并分页，前端负责展示。实现量较大，但可审计、可增量、不会把别人的文件错误挂到另一段对话。

### 方案 C：只展示全局归档文件

可复用现有文件库，但无法满足按会话浏览，也无法保证人物 ID 与对话统一。只保留为“我的素材库 / 全部产出”两个固定集合，不作为会话资产来源。

## 信息架构

### 第一层：全局轨道

保留现有最左侧导航。聊天、文件、洞察等板块仍在固定位置；底部增加主题按钮。图标按钮使用 Lucide，悬停提示名称，按下立即产生缩放/底色反馈。

### 第二层：聊天导航

聊天页左侧宽导航包含：

1. 会话搜索。
2. 固定置顶集合“我的素材库”和“全部产出”。
3. 用户置顶会话，支持图钉按钮切换并写入 `localStorage`。
4. 其余群聊/私聊，按最后消息时间倒序；筛选状态与选中状态不改变列表尺寸。

置顶只保存会话 ID，不改写聊天数据库。失效 ID 在读入时忽略，避免旧置顶破坏页面。

### 第三层：会话资产工作区

顶部依次为：会话身份、图钉/AI 等命令、统计条、分类 Tab 和检索框。Tab 固定为：

- `全部`：作品 + 文档 + Skills 工具 + 链接，不包含聊天文字。
- `作品`：图片、视频、音频、HTML/网页作品及可浏览创作文件。
- `文档`：PDF、Word、演示、表格、Markdown、文本等。
- `Skills 工具`：技能包、代码/工具包及明确标记为 skill 的产物。
- `链接`：从消息正文或应用消息中结构化提取的 URL。
- `聊天文字`：普通文本消息，独立计数和分页。

统计由服务端对同一分类器计算，Tab 数量与实际列表必须一致。检索覆盖标题、正文摘要、发送人显示名、扩展名和 URL；服务端分页，检索词原样参数化绑定，禁止拼接 SQL。

## 资产与人物数据契约

### 消息身份

`messages` 增加或重建以下字段：`local_id`、`sort_seq`、`raw_type`、`type`、`sender`、`sender_name`。`raw_type` 保存微信原始 64 位类型，`type = raw_type % 2^32` 保存基础类型。人物解析顺序为：正文中可信群前缀、`real_sender_id -> name2id`、私聊对端/机主规则、明确的未知占位。任何回退都保留审计原因，不把数字 ID 当昵称。

同一账号的旧快照与新快照不得同时写入结果。解析器通过会话集合、首条时间和消息覆盖关系识别严格子集快照，只选择覆盖更完整且更新的目录；无法确定时保留两个账号并在审计中报警，禁止静默合并。

### 资产证据

资产主键由 `message_uid + resource_evidence_signature + variant` 生成。证据签名只由规范会话范围、资源类型、`packed_info` 摘要、资源 hash 或应用消息 XML 文件标识等稳定证据构成；快照名、资源消息行号和资源明细行号只供审计，不参与身份。每条本地资产记录至少保存：会话、消息、本地只读源路径、可选归档 ID、资源 hash、媒体类型、预览类型、导出状态、失败原因。聊天消息、URL 等虚拟资产同样保存来源消息序号。

只有以下证据可以建立会话文件关系：

- `message_local_id` 与 `MessageResourceInfo.message_local_id` 精确相等；
- 同一 `chat_id` / 会话资源表范围；
- `packed_info` 中提取的资源 hash 与本机文件 hash/文件名精确对应；
- 应用消息 XML 中的明确文件标识与同一消息记录对应。

模糊标题、相近时间、同名文件只能作为“未确认候选”，不得进入会话正式资产统计。

## 本地浏览器预览

真实文件复用 `FilePreview` 和现有只读路由。卡片点击打开应用内预览面板；“在新标签页打开”生成本地 URL。图片、视频使用真实缩略图；其他类型使用统一的 Lucide/SVG 预设。外部链接明确标识域名并在新标签页打开。无本地文件的消息资产打开只读详情，不伪造可播放状态。

HTML 预览在本地路由中设置限制性 CSP/sandbox；下载型文件不内联执行。路径解析继续校验在允许根目录内。

## 主题与视觉

- 语义 token：画布、结构侧栏、浮层、一级/二级文字、分隔线、选择色、状态色；组件不直接依赖固定深色值。
- 浅色以明亮中性灰和白色层级为主，深色以黑/深灰层级为主；蓝、绿、橙、紫只承担命令或分类语义，避免单一色系占满页面。
- 系统字体优先，中文回退为 `PingFang SC` / `Microsoft YaHei`；紧凑工作台不使用营销式大标题。
- 卡片圆角不超过 8px；工具栏可使用克制的半透明材质，但不叠加多层玻璃。
- 主题初次跟随系统，用户选择持久化；`prefers-reduced-motion`、`prefers-reduced-transparency`、`prefers-contrast` 均有降级。
- 桌面保持三列关系；窄桌面收窄二级导航；移动端以可返回的会话列表和单列内容工作区切换，任何文字、Tab 和按钮不得相互遮挡。

## SOP 与数据更新

先快照 `data/wechat.db`、洞察状态和清单，再修解析器；随后只对 `work/decrypted/` 副本重建。若需重新解密，只读微信原始库并输出到新的副本目录。解析后运行人物/消息/重复账号审计，再生成 digest、delta 和受影响洞察。旧洞察不无脑覆盖。

文件与语音采用“能导出则导出、不能则记录原因”的状态机。图片、视频、文件和语音分别记录 `exported`、`thumbnail_only`、`missing_source`、`unsupported_codec`、`decrypt_failed`；SILK/AMR 尝试使用本机 ffmpeg/可用解码器，失败时保留原载荷与错误，不伪造音频。

## 验收标准

- `全部 = 作品 + 文档 + Skills 工具 + 链接`，且不含聊天文字；所有数量与分页结果一致。
- 置顶跨刷新保留，取消置顶立即生效；丢失会话不会导致页面报错。
- 每张卡可打开真实本地预览、外部链接或来源消息详情之一，不出现死点击。
- 人物 ID 审计中不存在“同一证据键映射到两个发送人”；未知映射有明确计数和原因。
- 重复账号快照不重复计入会话/消息；消息总量、首末时间、中文文本通过对账。
- 浅色、深色、减少动态、移动端和桌面端通过 Playwright 截图与交互回归。
- `git ls-files data archive work imports .env.local image_key.json` 无隐私文件；构建、单测、lint 与数据审计命令通过。
