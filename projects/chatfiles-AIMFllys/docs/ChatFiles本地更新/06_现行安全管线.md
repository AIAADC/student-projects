# 06 · 现行安全管线（2026-07）

本页是当前唯一可执行的本地更新入口。00-05 继续解释高水位、边界与历史背景，但其中的旧路径和旧脚本不得直接运行。

## 1. 不变的红线

- 原始微信、QQ 数据只读；所有解密、解析和提炼只写版本副本。
- 禁止手工覆盖或删除 `data/insights`、`data/wechat.current`、`archive` 中的既有成果；只允许审计通过后的正式激活流程做版本化移动与替换。
- `data/`、`archive/`、`work/`、`imports/`、密钥和身份配置永不进入 Git。
- QQ 正文未解密、微信 `.dat` 未物化、语音导出失败等必须保留真实失败状态，禁止用占位内容伪装成功。
- 任一 audit 未通过时禁止激活；失败候选和 previous 目录保留用于审计，不批量清理。

## 2. 微信版本快照与规范数据库

在线微信库必须通过原生 SQLCipher helper 生成版本快照。scanner 与 helper 必须使用已验收的明确路径，禁止按模糊文件名挑选旧诊断版本。

```powershell
npx tsx scripts/snapshotLiveWeChat.ts `
  --pid {{微信主进程PID}} `
  --account-root "{{精确账号根}}" `
  --output-root work/snapshots/live `
  --scanner "{{wechat-key-scanner.exe}}" `
  --snapshot-helper "{{sqlcipher-snapshot-helper.exe}}" `
  --run-id {{唯一run-id}}
```

只有 snapshot manifest 末态为 `validated`、`snapshot-runs.jsonl` 同 run 为 `complete` 的目录才可进入解析源。发布到 `work/decrypted/wechat/<run-id>` 前，应先在同盘 staging 中逐文件核对相对路径和 SHA-256，再 rename；不要让 `.incoming-*` 进入 parser source root。

```powershell
$run = '{{唯一run-id}}'
$env:CHATFILES_RUN_ID = $run
npx tsx scripts/parseWeChat.ts
npm run audit:chat:next
```

解析器只发布 `data/wechat.next`。`npm run audit:chat:next` 必须完成候选库的 source/output 行级身份闭合、规范 owner、消息类型和 UTF-8 来源核对；无参数的 `npm run audit:chat` 用于复审已激活的 `data/wechat.current`。

> [!IMPORTANT]
> **当前仓库没有经过测试的 chat/assets activate CLI，本流程必须停在已审计的 `.next` 候选。** 禁止手工 `Move-Item`、覆盖 current 或拼临时激活脚本；服务端继续读取原 `data/wechat.current`。未来正式激活命令至少必须满足：递归拒绝 bundle 内所有 symlink/junction；把 `index.json.runId`、数据库 `parse_runs/asset_runs`、数据库 SHA-256/大小和 audit 结果绑定为一份 receipt；使用 `validated / current_moved / rolled_back / activated` journal，并在异常中断后按 journal 与哈希恢复。缺少任一项都不得激活。

## 3. 洞察候选、闭合与激活

首次修复旧 owner 别名时，先在 `work/audits/` 写显式 alias map。它必须给出唯一 canonical owner、每个旧 owner 到 canonical owner 的映射，以及 strict source audit / 会话覆盖证据。普通后续更新若源洞察已经全是 canonical owner，不需要 alias map。

```json
{
  "version": 1,
  "canonicalOwner": "{{canonical-owner}}",
  "aliases": { "{{legacy-owner}}": "{{canonical-owner}}" },
  "evidence": [{ "kind": "strict-source-identity-audit", "path": "work/audits/{{audit}}.json" }]
}
```

构建候选：

```powershell
$run = '{{唯一run-id}}'

npm run insights:prepare -- `
  --run-id $run `
  --source data/insights

# 仅修复旧 owner 时，改用带证据映射的命令：
npm run insights:prepare -- `
  --run-id $run `
  --source data/insights.previous.{{previous-run-id}} `
  --alias-map work/audits/{{alias-map}}.json

npm run insights:distill -- --run-id $run
npm run insights:boards -- --run-id $run
npm run audit:insights
```

安全契约：

- `prepare` 只读 `data/wechat.current/wechat.db` 与 source，排他发布 `data/insights.next`；source、bundle、数据库必须位于规定角色路径内且不得是 symlink/junction。
- receipt 绑定活动数据库的 SHA-256 与大小、source manifest/state 哈希、alias-map 哈希和 baseline evidence。
- grown 会话使用 `(time, message_uid)` 稳定游标；旧 state 暂无 UID 时仍必须满足 `查询文本行数 == textCount 增长`，否则停止推进。
- `distill` 会读取本轮全部增量文本行，再做有效性筛选和稳定选择。`inputRows / eligibleRows / selectedRows / addedNuggets` 必须写入 receipt 并闭合；不是只读展示出来的几条。
- 旧语义要点只有全部字段相同才去重；`people / date / category / importance` 的差异必须保留。旧 summary 进入 `legacySummaries` 证据，不可静默丢弃。
- distill 在独立 staging 完成后才替换 candidate，并保留 `data/insights.prepared.<run-id>`；boards 同样先完整生成再切换，旧板保留在 candidate 的 `boards.pre-refresh.<run-id>`。
- audit 必须验证当前实质会话集合（本次为 494 个，实际数量以本机为准）、manifest/conv/state 一一对应、baseline evidence 全量存在、游标可解析、全部实际类别板计数闭合（本次为 13 类）、严格 UTF-8 和数据库指纹一致。

激活前停止服务：

```powershell
npm run insights:activate -- --run-id $run
npm run audit:insights -- --bundle data/insights
```

激活保留 `data/insights.previous.<run-id>`，并写 `data/.insights-activation.<run-id>.json`。如果 current 已移动而 candidate 发布失败，命令必须恢复 current 并将 journal 标为 `rolled_back`；异常中断后重跑同一命令会先尝试恢复。

## 4. 会话资产与文件归档

会话资产从已激活的 `data/wechat.current/wechat.db` 与同 run 版本快照构建：

```powershell
npx tsx scripts/buildConversationAssets.ts `
  --source-snapshot work/decrypted/wechat/{{run-id}} `
  --bundle data/chat-assets.next `
  --run-id {{run-id}}

npx tsx scripts/auditConversationAssets.ts --bundle data/chat-assets.next
```

审计通过后仍须保留 `data/chat-assets.next`，不得人工激活；正式 activate CLI 的准入要求见 §2。`npm run audit:assets` 只审计已激活的 `data/chat-assets.current`，不能替代上方针对 next 的显式审计，也不能证明 next 已进入 UI。

文件归档仍是 append-only：

```powershell
$env:CHATFILES_RUN_ID = '{{唯一run-id}}'
npm run ingest:files
```

它只新增经 SHA-256 验证的副本并发布 `data/library.next/{manifest.json,receipt.json}`。当前 UI 和部分脚本仍读取 `data/library.json`；在 reader 迁移或正式 dual-publish 工具完成前，不得宣称 `library.next` 已激活，也不得手工覆盖 `library.json`。
