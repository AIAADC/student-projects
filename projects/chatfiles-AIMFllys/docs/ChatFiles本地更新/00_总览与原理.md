# 00 · 总览与原理（幂等模型 + 高水位去重）

> [!CAUTION]
> **本页描述的是早期历史模型，不再代表当前代码，也不可按页内命令执行。** 现行解析器只发布 `data/wechat.next`，身份键、洞察游标和停服激活契约也已升级；实际更新必须从 [`06_现行安全管线.md`](06_现行安全管线.md) 开始。

> 本文讲清增量更新**为什么能既不漏新、又不重复分析**。理解了这套幂等模型，后面的步骤就只是按部就班。

---

## 1. 三个历史假设（仅用于理解旧策略）

1. **`data/wechat.db` 是每次整库重建的。** [`scripts/parseWeChat.ts`](../../scripts/parseWeChat.ts) 开头会 `fs.rmSync(outDbPath)` 再重建，并遍历 `work/decrypted/wechat/` 下**所有**账号。
   → **推论**：只要把"新消息 / 新账号"重新解密进 `work/decrypted/`，再跑一次 `parseWeChat.ts`，`data/wechat.db` 自动就是"最新全量"——新消息、新账号都在里面，会话主键 `wx:<account>:<username>` 保持稳定。**解析层天然幂等，不用做增量。**

2. **`data/insights/_manifest.json` 也是每次重写的。** [`scripts/prepChatDigests.ts`](../../scripts/prepChatDigests.ts) 选 `text_count >= 20` 的会话，重写清单（每条含 `convId / textCount / first / last`）。
   → **推论**：manifest 反映的是"**当前**每个会话有多少文本消息"。把**更新前**的 manifest 和**更新后**的 manifest 一比，就知道每个会话**长大了多少**。

3. **"已分析"的状态藏在 `data/insights/conv/<safe(convId)>.json` 里。** 每个会话一份，由提炼阶段的 agent 写。但它**不记录**"当时分析了多少条"——所以光看它无法判断"有没有新增"。
   → **推论**：需要我们**自己维护一个高水位状态**，把"每个会话已分析到的文本量 / 时间"固化下来。

---

## 2. 高水位线（high-water mark）模型

引入一个状态文件（本 SOP 维护，纯本地、gitignored）：

```
data/insights/_state.json
[
  { "convId": "wx:acct:xxx@chatroom",
    "analyzedTextCount": 1234,        // 上次分析时这个会话有多少条文本消息
    "analyzedLastTime": 1717500000,   // 上次分析覆盖到的最后一条消息时间(unix 秒)
    "analyzedAt": "2026-06-06T..." }, // 上次分析的时刻(信息用)
  ...
]
```

**delta（需要本轮分析的会话）的判定**：拿**更新后**的 manifest 和 `_state.json` 对：

| 情况 | 判定 | 处理 |
|---|---|---|
| convId 在 manifest，**不在** state，且 `textCount >= 20` | **新增会话** | 全量提炼，写**新** `conv/*.json` |
| convId 两边都有，且 `manifest.textCount - state.analyzedTextCount >= 阈值` | **长大的会话** | 只对 `time > analyzedLastTime` 的**尾部**消息提炼，**追加**进已有 `conv/*.json` |
| convId 两边都有，增量 `< 阈值` | **没实质新增** | **跳过**（不重复分析） |

> 阈值 `DELTA_MIN_TEXT`（建议 5–10 条新文本）避免为了一两句"在吗/收到"就重跑一个 agent。可按需调。

这样：**旧会话没新内容 → 一个 agent 都不会重跑**；长大的会话 → 只读它的新尾巴，旧 nugget 原样保留、新 nugget 追加。这就是"不重复分析之前分析过的"的机制保证。

---

## 3. 为什么"快照"是关键的第一步

`prepChatDigests.ts` 会**覆盖** `_manifest.json`。如果你直接重跑它，旧的 textCount 基线就没了，delta 无从算起。所以：

- **首次更新**：在重跑解析 / digest **之前**，把现有 `_manifest.json` 固化成 `_state.json`（把每个会话的 `textCount` 当作"已分析到的量"），并备份 `_manifest.json → _manifest.prev.json`。这一步在 [`01_前置与快照.md`](01_前置与快照.md)。
- **后续更新**：`_state.json` 已存在（上轮更新结束时更新过），直接拿它当基线，**不要**再用 manifest 覆盖它。

> 取舍说明：首次更新的基线来自"上次全量构建时的 manifest"，因此**上次构建之后、首次更新之前**这段时间里、已分析会话新增的少量消息，可能不会被回溯提炼（新增会话仍会被完整捕获）。这是为换取确定性与简单而做的、可接受的近似；此后每轮都精确按高水位推进。

## 4. 历史模型中的其余幂等假设

- **归档** [`scripts/archiveFiles.ts`](../../scripts/archiveFiles.ts)：用 `sha256` + 同名最大序号去重，**重跑只新增、不重复**——直接再跑即可补进新文件。
- **主题板** `data/insights/boards/*.md`：是跨会话综述，受新 nugget 影响的类**重综述**即可（或索性全 13 类重跑，成本相对小）。
- **服务端（历史假设）**：旧流程认为浏览器刷新即可见新数据；现行流程必须停服激活并重新审计，不能沿用“无需重启”的结论。
